# STU-972 — Connect arrows to text objects

## Approved design

Text objects become valid arrow endpoints with the same four edge anchors every
other connectable element has. Separately, `removeElements` learns to take a
deleted element's connectors with it — which closes STU-862 for every type, and
is less code than special-casing text.

Bounded path, approved in chat 2026-09-25. No spec file, no plan document.

## Contract

```ts
// src/lib/connector-drag.ts — one line
function canBeAnEndpoint(element: BoardElement): boolean {
  return element.type === 'sticky' || element.type === 'shape' || element.type === 'text'
}
```

```ts
// src/lib/board-mutations.ts — removeElements also drops connectors
// pointing at anything it removes, inside the SAME transact() so undo
// treats the element and its arrows as one step.
export function removeElements(board: WhiteboardDocState, ids: Iterable<string>): void
```

`TextItem` gains the six anchor props `StickyNote` already has:
`onAnchorDragStart`, `onAnchorKeyActivate`, `showAnchors`, `highlightedAnchor`,
and the two render paths those drive.

## Verified repo facts

Each checked in this session. Do not trust a line here with no location.

- `canBeAnEndpoint` at `src/lib/connector-drag.ts:26-28` returns
  `sticky || shape`. This is the only type gate in the connector path.
- `removeElements` at `src/lib/board-mutations.ts:32-40` deletes from
  `elementsMap` and `elementOrder` inside one `transact()`. It does **not**
  touch connectors today — that is STU-862.
- `getAnchorPosition` at `src/lib/connector-math.ts:9-20` takes a
  `BaseElement` and switches on the **anchor**, never on the element type. It
  computes from `x/y/width/height` only, so it already handles text correctly.
  Confirm with a test rather than by trusting this line. (The review found my
  count of its existing specs was wrong — six, not five. The file itself is
  untouched, which is what the check was actually about.)
- `StickyNote.tsx` holds the anchor pattern to copy — 6 references to the
  anchor props. `TextItem.tsx` currently has **0**.
- Anchors sit at `-5` offsets. That is not decoration: anchors overlapping the
  resize handles previously made both unclickable, and the offset is the fix.

## Assumptions

Phrased to invite correction rather than be inherited.

- I believe a connector re-renders when a text object's derived height changes,
  because height is stored on the element and connectors read it through
  `getAnchorPosition`. **Verify with a test that grows the text a line and
  asserts the anchor moved** — this is the one genuinely new thing about text
  as an endpoint.
- I believe anchors rendering during an active edit will not fight the
  textarea, since they sit outside the element's box. Not checked. Text is the
  only element whose anchors can appear over a live edit surface.

## Traps

Inherited from STU-953 and earlier; all were paid for once already.

- **jsdom does no layout and no CSS hit-testing.** Anchors are pointer-events,
  z-order and overlap — precisely what jsdom cannot see. Prove anchor
  clickability in a real browser.
- **Anything with parentheses or spaces is a style, not a class.**
  `pointer-events-stroke` as a `className` generates no CSS. Three separate
  bugs in this repo came from this.
- **`[data-testid^="text-"]` also matches `text-body` and `text-line`.** Pin by
  the exact id.
- **A live `.last()` locator re-resolves** when another element is drawn.
- **Properties-bar panels clip off the left edge** (STU-927, out of scope).
  Place E2E elements clear of it; `fill-pattern.spec.ts` uses x=280 on mobile.
- **Local UI state must never derive from shared document data** — the STU-953
  Critical. Relevant here if anchor visibility is ever tied to element data.

## Out of scope

- STU-927 (panel clipping), STU-962 (measure cache), STU-964 (unescaped export
  colours). Any NEW colour this ticket interpolates into the export must be
  escaped regardless.
- Connecting arrows to drawings or frames.
- Changing connector routing or arrowhead behaviour.
